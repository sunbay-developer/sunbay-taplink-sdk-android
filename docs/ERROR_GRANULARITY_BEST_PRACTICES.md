# SDK 半集成错误粒度最佳实践

## 一、错误粒度设计原则

### 1.1 核心原则

**错误粒度应该满足"可操作、可诊断、可分类"三个要求：**

1. **可操作**：错误信息能够指导用户或开发者采取明确的修复行动
2. **可诊断**：错误信息包含足够的上下文，便于问题定位
3. **可分类**：错误可以按照类型、严重程度、重试策略进行分类处理

### 1.2 粒度层次

```
┌─────────────────────────────────────────┐
│  错误粒度层次（从粗到细）                  │
├─────────────────────────────────────────┤
│ Level 1: 大类错误（用户可见）            │
│   - 设备问题、网络问题、支付问题          │
│   - 适用于：最终用户（ISO）              │
├─────────────────────────────────────────┤
│ Level 2: 中类错误（开发者可见）          │
│   - 连接失败、认证失败、参数错误          │
│   - 适用于：ISV开发者                     │
├─────────────────────────────────────────┤
│ Level 3: 细类错误（技术诊断）            │
│   - WebSocket连接失败、mDNS发现失败      │
│   - 适用于：技术支持、问题排查             │
├─────────────────────────────────────────┤
│ Level 4: 详细错误（调试信息）            │
│   - 包含堆栈、traceId、技术细节          │
│   - 适用于：SDK维护者、深度调试           │
└─────────────────────────────────────────┘
```

## 二、推荐错误粒度标准

### 2.1 面向最终用户（ISO）的粒度

**粒度级别：Level 1 - 大类错误**

**原则：**
- 只提供用户可理解和可操作的错误信息
- 隐藏技术细节，避免混淆
- 提供明确的解决建议

**示例：**

| 错误场景 | 粒度 | 用户消息 | 操作建议 |
|---------|------|---------|---------|
| 设备未连接 | 粗 | "设备未检测到" | "请检查线缆连接" |
| 网络问题 | 粗 | "网络连接失败" | "请检查WiFi连接" |
| 支付失败 | 粗 | "支付失败" | "请重试或联系客服" |

**不推荐：**
- ❌ "WebSocket连接失败，错误码1006，端口8443被防火墙阻止"
- ❌ "mDNS服务发现超时，5秒内未发现设备"
- ❌ "SSL握手失败，证书验证错误：CN不匹配"

### 2.2 面向开发者（ISV）的粒度

**粒度级别：Level 2-3 - 中细类错误**

**原则：**
- 提供足够的技术细节用于问题诊断
- 包含错误分类和重试策略
- 提供技术层面的解决方案

**示例：**

| 错误场景 | 粒度 | 开发者消息 | 技术细节 |
|---------|------|-----------|---------|
| 设备未连接 | 中 | "LAN连接失败：设备未找到" | "mDNS发现超时，建议手动配置IP" |
| 网络问题 | 中 | "WebSocket连接失败" | "端口8443被阻止，检查防火墙" |
| 认证失败 | 中 | "连接认证失败" | "appId或secretKey无效" |

**推荐格式：**
```json
{
  "errorCode": "L1001",
  "errorName": "DEVICE_NOT_FOUND",
  "message": "Payment device not found on network",
  "category": "LAN_CONNECTION",
  "retryable": true,
  "suggestedAction": "Check device network connection",
  "technicalDetails": "mDNS discovery timeout after 5 seconds"
}
```

### 2.3 面向技术支持（SDK维护者）的粒度

**粒度级别：Level 3-4 - 细类+详细错误**

**原则：**
- 包含完整的错误上下文
- 提供traceId、堆栈信息
- 包含系统状态、网络状态等诊断信息

**示例：**
```json
{
  "errorCode": "L1001",
  "errorName": "DEVICE_NOT_FOUND",
  "message": "Payment device not found on network",
  "details": {
    "category": "LAN_CONNECTION",
    "severity": "ERROR",
    "retryable": true,
    "suggestedAction": "Check device network connection",
    "technicalDetails": "mDNS discovery timeout after 5 seconds",
    "networkInfo": {
      "wifiConnected": true,
      "networkType": "WIFI",
      "ipAddress": "192.168.1.100"
    },
    "deviceInfo": {
      "sdkVersion": "1.0.0",
      "osVersion": "Android 12",
      "deviceModel": "SM-G991B"
    },
    "traceId": "trace-12345",
    "timestamp": "2025-12-22T10:30:00Z"
  }
}
```

## 三、不同场景的粒度建议

### 3.1 连接错误粒度

| 错误类型 | 推荐粒度 | 理由 |
|---------|---------|------|
| **连接失败** | 中粒度 | 区分连接模式（App to App/LAN/Cable）即可 |
| **连接超时** | 中粒度 | 不需要区分是网络超时还是设备响应超时 |
| **连接被拒绝** | 中粒度 | 统一为"连接被拒绝"，不需要区分拒绝原因 |
| **设备未找到** | 细粒度 | 需要区分是mDNS失败还是IP配置错误 |

**示例：**
```kotlin
// ✅ 推荐：中粒度
"L1001" -> "设备未找到"  // 不区分mDNS还是手动配置失败

// ❌ 不推荐：过细粒度
"L1001" -> "mDNS发现失败"
"L1002" -> "手动IP配置失败"
"L1003" -> "DNS解析失败"
```

### 3.2 认证错误粒度

| 错误类型 | 推荐粒度 | 理由 |
|---------|---------|------|
| **认证失败** | 中粒度 | 统一为"认证失败"，不暴露具体原因（安全考虑） |
| **凭证无效** | 中粒度 | 区分appId错误还是secretKey错误即可 |
| **会话过期** | 粗粒度 | 统一为"会话过期" |

**示例：**
```kotlin
// ✅ 推荐：中粒度
"G2001" -> "认证失败：凭证无效"  // 不区分是appId还是secretKey

// ❌ 不推荐：过细粒度
"G2001" -> "认证失败：appId格式错误"
"G2002" -> "认证失败：secretKey长度不足"
"G2003" -> "认证失败：appId未注册"
```

### 3.3 交易错误粒度

| 错误类型 | 推荐粒度 | 理由 |
|---------|---------|------|
| **交易失败** | 细粒度 | 需要区分失败原因（余额不足、卡片拒绝等） |
| **交易超时** | 中粒度 | 统一为"交易超时"，不需要区分是网络还是设备超时 |
| **交易锁定** | 粗粒度 | 统一为"交易锁定" |

**示例：**
```kotlin
// ✅ 推荐：细粒度（业务相关）
"T2004" -> "余额不足"
"T2005" -> "卡片被拒绝"
"T2006" -> "交易限额超限"

// ✅ 推荐：中粒度（技术相关）
"T1003" -> "交易超时"  // 不区分具体超时原因
```

### 3.4 硬件错误粒度

| 错误类型 | 推荐粒度 | 理由 |
|---------|---------|------|
| **USB连接失败** | 细粒度 | 需要区分是权限问题还是硬件问题 |
| **设备未检测到** | 中粒度 | 统一为"设备未检测到" |
| **协议错误** | 细粒度 | 需要区分协议类型（AOA/VSP/RS232） |

**示例：**
```kotlin
// ✅ 推荐：细粒度
"C1003" -> "USB权限被拒绝"
"C1004" -> "USB设备不兼容"
"C3001" -> "AOA协议初始化失败"
"C3002" -> "VSP通信错误"

// ❌ 不推荐：过细粒度
"C3001" -> "AOA协议初始化失败：USB描述符读取失败"
"C3002" -> "AOA协议初始化失败：USB配置设置失败"
```

## 四、粒度设计检查清单

### 4.1 粒度是否合适的判断标准

**✅ 粒度合适：**
- [ ] 错误信息能够指导明确的修复行动
- [ ] 不需要额外的诊断信息就能理解问题
- [ ] 错误分类清晰，便于程序化处理
- [ ] 不会暴露敏感信息（如密钥、内部实现）

**❌ 粒度过细：**
- [ ] 错误信息包含过多技术细节，用户无法理解
- [ ] 错误码数量过多，难以记忆和维护
- [ ] 错误信息暴露了内部实现细节
- [ ] 多个错误码实际上需要相同的处理逻辑

**❌ 粒度过粗：**
- [ ] 错误信息无法指导具体的修复行动
- [ ] 需要额外的诊断才能定位问题
- [ ] 无法区分需要不同处理策略的错误
- [ ] 错误信息对开发者没有帮助

### 4.2 粒度设计决策树

```
开始
  │
  ├─ 用户能否理解并操作？
  │   ├─ 否 → 粒度过细，需要简化
  │   └─ 是 → 继续
  │
  ├─ 开发者能否诊断问题？
  │   ├─ 否 → 粒度过粗，需要细化
  │   └─ 是 → 继续
  │
  ├─ 错误是否需要不同处理策略？
  │   ├─ 是 → 需要细化
  │   └─ 否 → 可以合并
  │
  └─ 是否暴露敏感信息？
      ├─ 是 → 需要简化或隐藏
      └─ 否 → 粒度合适 ✓
```

## 五、实际应用建议

### 5.1 错误码数量建议

| 错误类型 | 推荐数量 | 说明 |
|---------|---------|------|
| **通用错误** | 5-10个 | 系统级错误，数量少但覆盖面广 |
| **连接错误** | 10-15个 | 按连接模式分类，每种模式3-5个 |
| **交易错误** | 15-20个 | 业务相关，需要细粒度区分 |
| **参数错误** | 8-12个 | 按参数类型分类 |
| **硬件错误** | 10-15个 | 按硬件类型和错误原因分类 |
| **总计** | **50-80个** | 平衡覆盖面和可维护性 |

### 5.2 分层错误信息设计

**推荐实现：**

```kotlin
data class ErrorInfo(
    // Level 1: 用户友好消息（ISO）
    val userMessage: String,
    
    // Level 2: 开发者消息（ISV）
    val developerMessage: String,
    
    // Level 3: 技术细节（技术支持）
    val technicalDetails: TechnicalDetails?,
    
    // 错误分类
    val category: ErrorCategory,
    val severity: ErrorSeverity,
    val retryable: Boolean,
    val suggestedAction: String
)

data class TechnicalDetails(
    val errorCode: String,
    val errorName: String,
    val traceId: String?,
    val networkInfo: NetworkInfo?,
    val deviceInfo: DeviceInfo?,
    val stackTrace: String?  // 仅调试模式
)
```

### 5.3 错误粒度示例对比

#### 场景1：设备连接失败

**❌ 粒度过细：**
```

L1002: mDNS服务发现超时
L1003: mDNS服务发现网络不可达

L1006: 手动IP配置端口不可用
```

**❌ 粒度过粗：**
```
L1001: 连接失败
```

**❌ 粒度过细：**
```
C1001: USB设备未连接

C1003: USB设备未授权
C1004: USB设备权限被拒绝

C1006: USB设备描述符读取失败
C1007: USB设备配置设置失败
```

**✅ 粒度合适：**
```
C1001: USB线缆未连接
C1002: USB设备未检测到
C1003: USB权限被拒绝
C1004: USB设备不兼容
```

**❌ 粒度过粗：**
```
C1001: USB错误
```

## 六、总结

### 6.1 最佳实践原则

1. **用户层（ISO）**：粗粒度，4-6个大类错误
2. **开发者层（ISV）**：中粒度，50-80个错误码
3. **技术支持层**：细粒度，包含完整技术细节

### 6.2 粒度设计黄金法则

> **"错误粒度应该让用户知道做什么，让开发者知道为什么，让技术支持知道如何修复"**

### 6.3 推荐粒度标准

| 维度 | 推荐粒度 | 错误码数量 |
|------|---------|-----------|
| **用户可见** | 粗粒度 | 4-6个类别 |
| **开发者可见** | 中粒度 | 50-80个错误码 |
| **技术支持** | 细粒度 | 包含完整上下文 |

### 6.4 关键指标

- ✅ **可操作性**：90%的错误能够直接指导修复行动
- ✅ **可诊断性**：80%的错误能够快速定位问题
- ✅ **可维护性**：错误码总数控制在100个以内
- ✅ **用户体验**：最终用户看到的错误不超过10种类型
