## Why this is one plan, not decomposed features

The deliverable is a single internal mechanism — one `EstablishedRecoveryCoordinator` that owns every established-fault across all adapters — with tightly coupled seams in `ConnectionManager`, `PaymentManager`/`ResponseProcessor`, and the kernels. design §2 explicitly rejects per-kernel decomposition (option A). The coordinator is not observably correct until its interception, epoch, callback-dedup, and continuation seams are wired together; splitting it into independently-shippable features would leave intermediate states that cannot satisfy any AC. The steps below are ordered layers of one change, each leaving the tree buildable.

## Blockers — NOT verifiable in JVM (record, never claim passing)

- B1 — VSP/RS232/AOA trusted identity-anchor capture (`UsbDevice.serialNumber` not captured today) AND non-LAN Host-side continuation of the original response path after transport loss. Requires a Host-side approved spec/SCR (current Host rebind spec is LAN-only, onOpen only). JVM can only prove callback/traceId mapping retention + route re-attach.
- B2 — SUB_SCREEN screen-initialization readiness (transport-connected-but-screen-not-ready must not count as success).
- B3 — USB physical re-enumeration/attach, replug, port power-down (R12 "wait once within budget").
- B4 — Local AIDL process-restart semantics (process death must not be presented as resumable execution).
- B5 — AOA Accessory shared classes (audit only; no public client route; no device coverage claim).

These require maintainer-authorized device/real-backend testing and must be reported as unexecuted, not passing.
